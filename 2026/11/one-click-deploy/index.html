本地一键部署脚本：push 即上线

✍️ 博主 📅 令和8年11月7日 ⏱ 阅读约 18 分钟
#独立博客 #教程 #Hexo
📚 独立博客实战 · 第 4 篇（上线线）第 2 篇把站推上线，第 3 篇处理地址，这一篇处理"每次发文章都要重复一遍的那五条命令"。全季定位是不用 GitHub Actions，所以这条脚本要自己写。写完顺手发现了一个存在很久的问题——每次部署都在提交无关变更。

先复盘一次真实事故。

那天我发完第 15 篇，链条是这样的：

bashbash
1
git commit -m "post: ..." && git push -f origin gh-pages

执行完，终端打印了 On branch gh-pages / nothing to commit, working tree clean，退出码 1。我扫了一眼，心想”大概是没变更，那应该已经推过了”，就去干别的了。

半小时后检查线上，文章是 404。

真实原因是：这条命令被环境重跑了一次。 第一次跑时 commit 成功、push 也成功；第二次跑时 commit 返回”没有变更”，&& 短路，push 被跳过——但我的终端输出没有区分这两次。而 commit 里的 -q 又把成功那次的输出吞了。

这五条命令的危险不在于麻烦，在于每一步失败都可能是安静的。

这篇就是把它们收进一条命令，并且给每一步加上”失败必须吵醒我”的检查。

一、为什么不用 hexo deploy

Hexo 自带部署能力，装个 hexo-deployer-git 就能 hexo deploy 一把梭。我不用它，原因很具体——在这台机器上它是坏的。

图 1：同一台机器、同一个仓库、同一个 SSH key，唯一变量是”谁在调 git”。

现象是 hexo deploy 退出，工作树看起来”做了事”（.deploy_git 里内容变了），但远端没更新。真实原因是 Git 的 dubious ownership 检查：.deploy_git 目录的属主 SID 与当前用户不一致，hexo 内部 spawn 的 git 进程用的身份和我在 shell 里用的不同，于是被拒绝。

最省事的解法不是修权限，而是绕过 hexo，直接调 git——我在 shell 里 cd .deploy_git 之后，git add / commit / push 一直都能正常工作。

📌 一个通用判断当工具 A（hexo）调用工具 B（git）失败，而你手动跑 B 成功时，问题在"A 给 B 的环境"，不在 B 本身。改权限、改所有者、加 safe.directory 都是在猜；最快的验证是"手动跑一遍同样的命令"，能过就说明该换调用方式。

代价也很明确：hexo deploy 帮我做的那些事（清目录、复制产物、切分支、提交、推送），现在要自己写。

#!/usr/bin/env bash
set -euo pipefail

BRANCH="gh-pages"
SITE_URL="https://molunanli.github.io/Blog"
PORT=4000
MSG="${1:-post: update $(date '+%Y-%m-%d %H:%M')}"

say()  { printf '\033[36m▸ %s\033[0m\n' "$*"; }
ok()   { printf '\033[32m✓ %s\033[0m\n' "$*"; }
die()  { printf '\033[31m✗ %s\033[0m\n' "$*" >&2; exit 1; }

cd "$(dirname "$0")"
[ -f "_config.yml" ] || die "这里不是 Hexo 站点根目录"

# 1. 端口占用
if netstat -ano 2>/dev/null | grep -q ":$PORT .*LISTENING"; then
    die "端口 $PORT 有 hexo server 在跑，它会把 db.json 写回去"
fi

# 2-3. 清缓存 + 生成
rm -f db.json
npx hexo generate > /tmp/hexo-gen.log 2>&1 || { tail -20 /tmp/hexo-gen.log >&2; die "generate 失败"; }

# 4. 核验：最新文章的 slug 必须出现在首页
NEWEST=$(ls -t source/_posts/*.md | head -1)
SLUG=$(basename "$NEWEST" .md)
grep -q "$SLUG" public/index.html || die "首页里找不到 $SLUG —— 大概率是缓存问题"

# 5. 推送（commit 与 push 必须是两条独立命令）
cd .deploy_git
[ -f .git/index.lock ] && rm -f .git/index.lock
git remote remove origin 2>/dev/null || true
git remote add origin git@github.com:molunanli/Blog.git
git checkout -B "$BRANCH" >/dev/null 2>&1
find . -mindepth 1 -maxdepth 1 ! -name '.git' -exec rm -rf {} +
cp -rf ../public/. .
git add -A
git diff --cached --quiet && say "无变更" || git commit -q -m "$MSG"
git push -f origin "$BRANCH" 2>&1 | tail -2

# 6. 线上确认
for i in $(seq 1 8); do
    code=$(curl -s -o /tmp/chk.html -w '%{http_code}' "$SITE_URL/")
    [ "$code" = "200" ] && grep -q "$SLUG" /tmp/chk.html && { ok "线上已生效"; exit 0; }
    printf '  第 %d 次：%s，15 秒后重试\n' "$i" "$code"
    sleep 15
done
die "推送成功但线上未生效，稍后再看"

（完整版比我贴的多了颜色输出、日志落盘和错误信息，逻辑一样。）

三、每一道检查在挡什么

图 2：红框两步最容易被省掉，也最容易骗过自己。

第 1 步：查 4000 端口。 这个坑我踩过——本地开着 hexo server 时，它会周期性地把 db.json 写回去。你删了缓存、重新 generate，读到的还是旧 db，于是文章详情页更新了，但首页和归档里没有这篇。表现是”页面能打开，列表里找不到”，很容易误判成”是不是标签没配对”。

第 2 步：删 db.json。 同理。这是 Hexo 的数据库缓存，删了没有副作用，只是下次生成慢一点。我把它当成”生成前必做的清场”。

第 3 步：generate。 注意把输出重定向到日志，失败时打印尾部——否则 hexo generate 的报错会被后续步骤的输出淹没。

第 4 步：核验产物。 这是整个脚本里我最喜欢的一步，也是最容易被省掉的一步。

它做的事很土：取最近修改的那篇文章，看它的 slug 有没有出现在 public/index.html 里。 就这么一句 grep，能挡住上面第 1、2 步漏掉的缓存问题，也能挡住”改了文章但拼错文件名”这类事。

“构建成功”和”构建出了你要的东西”是两件事。 少这一步，你永远只能靠肉眼去线上确认。

第 5 步：五条命令分开跑。 具体的坑：

  • commit 和 push 不能用 && 串（本文开头那起事故）
  • git add -A 在文件多时会跑十几秒，别把它和别的命令串在一条长链里，容易被中断
  • 先删 .git/index.lock（上次异常退出会留下锁，之后所有 git 操作都报错）

第 6 步：线上轮询。 推送成功不等于上线成功。GitHub Pages 收到推送后还要构建，通常几十秒；这段时间访问新地址是 404。我固定重试 8 次、每次 15 秒，够了。

四、脚本跑通之后，我发现它在提交假变更

第一次跑这个脚本，一切正常。但它的输出里有一行让我停下来看了两遍：

我那次并没有改任何内容。 只是把流程重跑了一遍，它却提交了 17 个文件。

内容一个字没变，只是”相关文章”列表里两篇的先后换了位置。

根因：排序没有兜底

主题里”相关文章”的算法是：同分类 +3 分、每个共同标签 +1 分，按分数排序取前 4。 问题在于：

javascriptjavascript
1
.sort(function (a, b) { return b.s - a.s; })

当两篇文章得分完全相等时，比较函数返回 0，谁在前面取决于输入顺序。而输入来自 site.posts.data——一个 Warehouse 集合，它的迭代顺序跟文件系统读取顺序有关，每次构建都可能不同。

于是：同分 → 顺序随机 → 每次构建产出不同 → 每次部署都夹带一堆无关 diff。

修它：给排序加第二个键

javascriptjavascript
1
2
3
4
5
.sort(function (a, b) {
    return (b.s - a.s)
        || (b.p.date.valueOf() - a.p.date.valueOf())
        || (a.p.path < b.p.path ? -1 : a.p.path > b.p.path ? 1 : 0);
})

规则很简单：永远不要让”顺序未定义”的全等项存在。 分数相同就比时间，时间相同就比路径。总有一个键能把顺序定死。

然后发现，同样的问题有五处

图 3：五个模板，同一个病根——迭代 Warehouse 集合时没排序。

位置 症状
post.ejs 相关文章 同分文章互换位置
post.ejs 文章标签 page.tags 原始顺序不稳
post-card.ejs 列表标签 同上
sidebar.ejs 热门标签 按数量取前 10，数量相同时入选的标签会变
archive.ejs 热力图 JSON 的键序随遍历顺序变化

修法都一样：site.tags.sort('length', -1) 改成先 toArray() 再 .sort((a,b) => (b.length - a.length) || a.name.localeCompare(b.name))；forEach 集合前先 toArray().sort(...)。

还有两处，模板根本管不到

function fixSearchJson(file) {          // 把每个条目的 tags 数组排序
  const raw = fs.readFileSync(file, 'utf8');
  const next = raw.replace(/"tags":\[(.*?)\]/g, (whole, inner) => {
    const items = inner.split(',').map(s => s.trim()).filter(Boolean);
    if (items.length < 2) return whole;
    return '"tags":[' + items.slice().sort(cmp).join(',') + ']';
  });
  if (next === raw) return false;
  fs.writeFileSync(file, next, 'utf8');
  return true;
}

function fixAtomXml(file) {             // 把同一 entry 里连续的 <category> 行排序
  // 逐行扫描，收集连续的 <category .../> 行，排序后写回
}

hexo.extend.filter.register('after_generate', function () {
  fixSearchJson(path.join(hexo.public_dir, 'search.json'));
  fixAtomXml(path.join(hexo.public_dir, 'atom.xml'));
});

注意这里是”改产物”而不是”改源头”——严格说是治标。但对这两个文件，源头在第三方生成器里，改它等于 fork 一个包；而这个排序是纯粹的规范化，不影响语义。在边界上做一次确定化，比改别人的代码划算。

怎么验证修好了

不用肉眼看页面。连续构建两次，比产物。

diff -rq buildA public | wc -l

数字变化的完整过程：

阶段 差异文件数
什么都没改 33

那个 0 我一直留到最后才相信——连跑三次都是 0，才敢写进这篇。

⚠️ 为什么值得花时间修这个不是因为"强迫症"。假 diff 会掩盖真变更：一次提交里 17 个文件的顺序变化，加上你真正改的那 1 个文件，你根本没法从 commit 里看出"这次发版到底动了什么"。
而且它会持续污染部署分支的历史——三个月后回头看，全是无意义的 commit。这类问题的特点是没有报错、页面完全正常，只有"比两次构建产物"才能发现。

五、失败排查表

跑这个脚本时实际遇到过的错，按出现频率排：

现象 原因 处理
nothing to commit 但确实改了 hexo generate 没跑或跑失败 看 /tmp/hexo-gen.log；先手动 generate 一次
git 报 index.lock 存在 上次异常退出留下的锁 确认没有 git 进程在跑，再删 .git/index.lock
dubious ownership 目录属主与当前用户不符 别用 hexo deploy，直接调 git；或加 safe.directory
文章能打开，但首页/归档里没有 db.json 缓存 + server 占用 停 server → 删 db.json → 重新生成
推送成功但线上 404 Pages 还在构建 等 30~60 秒重试；先确认旧页面仍 200 证明站点活着
generate 突然失败、报写入错误 磁盘满（ENOSPC） 清 public/ 与临时目录；这台机器上会周期性出现
脚本跑到一半被中断 命令行太长被掐 拆成短命令；脚本里避免超长 && 链

最后一行补充一句：长命令链是脆的。我现在连”清树 + 复制”都拆成两步写，就是为了出错时能知道断在哪。

六、什么时候才值得换 GitHub Actions

这一季不用 Actions，理由不是”反对工具”，是现在不需要：

情况 用本地脚本 用 Actions
一个人、一台机器写作 ✅ 简单，零配置 多一层 YAML 要维护
想在手机上发文章 ❌ 做不到 ✅ 推到仓库就自动发布
多台电脑轮流写 ⚠️ 每台都要装环境 ✅ 环境统一
想定时发布 / 定时构建 ❌ 得开着电脑 ✅ cron 天然支持
出问题时要能一眼看懂 ✅ 一百行 bash，全是自己写的 ⚠️ 要读 workflow 日志

我自己的判断线是：只要还满足”一台电脑、想发的时候人在电脑前”这两条，本地脚本就够了。 一旦想在地铁上用手机改错别字发出去，就该切 Actions 了——那时候这笔复杂度是值得付的。

七、一个还没解决的问题

脚本放在 my-blog/deploy.sh，但站点源码本身没有版本控制——只有 .deploy_git 是 git 仓库（那是产物，不是源码）。也就是说：

  • 脚本丢了就没了，没有历史可回滚
  • 主题改动、文章源文件都没有版本记录
  • 想换机器时，只能整目录拷

这是个真实的结构性问题。正确做法是把 my-blog（排除 public/、node_modules/、.deploy_git/）也纳入一个仓库——但那是另一篇的事，我还没做。

所以这篇的结尾不是”大功告成”，是：工具链能用了，但地基还差一层。
