先不买域名，但把后路留好

✍️ 博主 📅 令和8年11月5日 ⏱ 阅读约 16 分钟
#独立博客 #教程 #Hexo
📚 独立博客实战 · 第 3 篇（上线线）第 2 篇把站推上了线，这一篇处理"地址"这件事。第 1 篇《为什么 2026 年还要自己搭一个博客》算过总账，结论是"一年 0 元"——其中省掉的最大一笔就是域名。所以这一篇要回答的是：这笔钱现在不花，代价是什么，怎么把代价压到最低。

先把我这个站的真实配置摊开，省得你猜：

项 现在的值
站点地址 https://molunanli.github.io/Blog/
根路径（root） /Blog/
永久链接 :year/:month/:slug/，即 /2026/09/xxx/
域名 没有
评论 Giscus，绑定 molunanli/Blog 仓库，mapping 为 pathname
费用 域名 0 元 + 托管 0 元

这不是”推荐配置”，只是一个刚好够用、且还没到必须升级的配置。这篇讲的就是它为什么够用、以及什么时候会不够用。

一、什么时候该买域名

先给判断标准，再谈技术。下面五条里任何一条成立，就该买了：

信号 说明
要当作品集或简历里的链接 xxx.github.io/repo/ 挂在简历上，说服力打折
国内读者占多数，且要求稳定打开 github.io 在国内访问时好时坏，这是最硬的痛点
需要用域名做邮箱 hi@yourname.com 需要一个你能改 MX 记录的域名
已经有稳定读者 此时迁移成本最低——读者会跟着你走，越晚越难
想摆脱”随时可能变”的托管策略 域名是你的，托管可以随时换；反过来不行

反过来说：如果一条都不成立，不买是对的。 域名不是”技术人的成年礼”，一年几十块也不是关键，关键是买早了会带来维护负担（续费、DNS、证书、备案判断），而你现在没有需要它解决的问题。

我的情况是：五条都不成立。所以这篇文章写的是”怎么把不买这件事做扎实”，不是”怎么买”。

二、免费的账：拿到五项，付出五项

图 1：右栏五项里，只有最后一项是现在能提前处理的。

你拿到的： 零成本、HTTPS 自动签发（GitHub 用 Let’s Encrypt 签，到期自动续，你什么都不用管）、不用备案、零运维、今天就可用。

你付出的： 网址长、多一层 /Blog/ 子路径、国内访问波动、品牌记在别人的域名下、将来换域名时所有链接要重做。

第三项值得展开一句，因为它被误解得最多。

📌 澄清一个常见误解"用 GitHub Pages 不用备案"——对，但原因不是"你没有域名"，而是服务器在境外。备案管的是境内服务器。所以：
① 现在没域名 + GitHub Pages → 不用备案
② 买了域名 + 仍指向 GitHub Pages → 依然不用备案
③ 买了域名 + 指向国内服务器 → 必须备案
换句话说，备案跟你买不买域名无关，跟你把站放在哪有关。这一条想清楚了，将来做决定会轻松很多。

三、五项代价里，只有一项现在能付

前四项——网址长、子路径、访问速度、品牌——只有买了域名才会消失，现在做什么都无用。你不可能靠写代码让 github.io 变短。

只有第五项「将来换域名的成本」，是现在就能提前付掉的。而且现在付，几乎不花钱；等有五十篇文章再付，就是一场大扫除。

这就是这篇的全部意义：把一次未来的大改，拆成现在的小习惯。

四、一个网址，其实由三段拼起来

要谈”改哪里会断”，先得看清网址的解剖结构。

图 2：https://molunanli.github.io + /Blog + /2026/09/pc-repair-first-lesson/，三段各有各的配置项。

① 域名 对应 _config.yml 的 url。换它，等于换门牌号。

② 根路径 对应 _config.yml 的 root。现在因为站挂在仓库子路径下，所以是 /Blog/。如果买了域名并把站放到域名根目录，这里就变成 /。 这是很多人忽略的一段。

③ 永久链接 对应 permalink: :year/:month/:slug/。它决定每篇文章的具体地址。

现在关键问题来了：

换了域名，旧地址会不会自动跳转到新地址？

GitHub 官方文档的说法是：为 Pages 站点配置自定义域名后，Pages 的默认域名会重定向到自定义域名。所以 molunanli.github.io 这一层，大概率会由 GitHub 帮你跳。

但这里有个我必须标”待确认”的地方：

⚠️ 重定向只解决域名，不解决路径官方文档讲的是"默认域名重定向到自定义域名"，但没有明确说明 project site 的子路径会怎么处理——`molunanli.github.io/Blog/2026/09/x/` 到底跳到 `example.com/2026/09/x/`，还是 `example.com/Blog/2026/09/x/`，我没有实测，标待确认。
而这个区别恰恰是要命的：前者说明 root 从 `/Blog/` 变成了 `/`，所有含 `/Blog/` 的链接全断；后者说明 root 没变，链接还能活。
验证方法：买之前先用一个不重要的子域（比如 `test.yourdomain.com`）挂上去试一次，看旧地址落在哪。十分钟的事，能省掉一场迁移事故。

工程上的正确做法不是”赌 GitHub 会救我”，而是：假设旧链接全断，倒推出现在该做什么。

五、把本站的实际情况摊开

写这一节之前我查了一遍自己的站，结果不太好看。

111 处写死的绝对地址 https://molunanli.github.io/Blog/...，分布在 20 篇文章里。0 处用了 root 相对路径。也就是说：全站只用了一种写法，而那种写法对域名变化最敏感。

更难看的是另一件事。我在写这个栏目总目录那篇时，给 about 页加了 7 个链接，写成了：

texttext
1
href="/2026/11/pc-repair-handbook-index/"

少了 /Blog/ 前缀。构建没报错，页面看起来也正常，点下去全是 404。这不是理论推演，是昨天刚发生、今天才发现的事故。

⚠️ 这类错误为什么特别难发现因为它在构建和本地预览里都是"成功"的。Hexo 不会检查你手写的 href 指向哪里，`hexo generate` 的报告里只有"Generated: XX files"。本地用 server 预览时，`/2026/...` 这个路径甚至可能真的能打开（取决于 server 的 root 处理），一上线就死。
唯一可靠的检查方式：对生成后的 HTML 提取所有站内 href，逐个去线上 curl 状态码。肉眼扫是扫不出来的。

有意思的是：同一个站里，图片路径从来没出过这个问题。

图片我写的是相对路径 images/domain/01.svg，构建后自动变成 /Blog/images/domain/01.svg。原因在渲染器：hexo-renderer-marked 默认开着 prependRoot，会把相对路径的图片和链接自动补上 root 前缀。

所以规律很清楚：

你写的 构建后 换域名 换 root
images/x.svg（相对） 自动补 root ✅ 安全 安全
/2026/09/x/（手写绝对） 原样输出 ❌ 安全 断
https://molunanli.github.io/Blog/2026/09/x/ 原样输出 ❌ 断 断

图片是安全的，链接不是。 因为图片走了渲染器，链接走了你自己的手。

六、三种写法，怎么选

图 3：③ 最稳，但代价最大——它把文章绑死在 Hexo 上。

① 写死的绝对地址（本站现状）。优点是可移植：文章复制到 Typora、Notion、公众号后台，链接照样能点。缺点是换域名要批量替换。111 处替换听起来多，其实一条 sed 就完了——真正的风险不是数量，是混用：如果站里同时有绝对地址和 root 相对路径，一次替换改不干净，你会漏掉一半。

② 以 root 开头的路径（/Blog/2026/...）。换域名不怕，换 root 要替换。缺点是在本地 Markdown 编辑器里点不开（它不知道 /Blog/ 是哪个站）。注意：这恰恰是我昨天写 404 的那种写法——省掉一个前缀就死，而且不留痕迹。

③ post_link 标签（Hexo 内置的标签插件，构建时按 slug 解析成真实地址）。它是唯一”换什么都不怕”的写法，因为它只依赖 slug。代价是：文章一旦离开 Hexo 就废了，粘到别处是一串没人认识的标签。

这里必须诚实说取舍。如果你的文章要长期保持”纯 Markdown、随时能搬到别处”（我确实是这么要求的），那就不该用 ③。可选的是 ① 或 ②，而且必须全站只用一种。

我的选择是 ①（绝对地址），理由很实际：文章的可移植性 > 迁移时的替换成本。111 处替换是十分钟的活，而文章绑死在某个生成器上，是永久性的债。

💡 一条比"选哪种"更重要的纪律全站只允许一种站内链接写法。混用才是最贵的：你会同时承担两种写法的缺点，而且每次替换都要人工判断"这处改了没有"。
定规矩的方式很简单：写完一篇，跑一次 grep -o 统计各写法的数量，只要出现第二种写法，当场改掉。成本一分钟。

七、现在就该做的四件事

第一件：统一下链接写法。 见上一节。本站现状是全绝对地址（111 处）——已经统一，不用动。你要做的是检查自己有没有混用。

第二件：图片坚持相对写法。 这一条不用做，别改就行。prependRoot 已经帮你处理了，反而是”为了保险”改成绝对地址会把安全的东西弄不安全。

第三件：把 Giscus 的 mapping 从 pathname 换掉。 这条最容易被漏，因为它在主题配置里，不在文章里。

现在本站的配置是：

yamlyaml
1
2
3
4
giscus:
  repo: molunanli/Blog        # 与域名无关，安全
  repoId: R_kgDOUMGUlQ        # 与域名无关，安全
  mapping: pathname           # ← 这里有问题

repo 和 repoId 指向的是仓库，跟域名没关系，换了域名也不用改——这点设计得很好。

但 mapping: pathname 的意思是：用页面的路径去匹配对应的 Discussion。 现在每篇文章的 pathname 是 /Blog/2026/09/xxx/。一旦 root 从 /Blog/ 变成 /，pathname 就变成 /2026/09/xxx/——对不上原来的 Discussion，所有历史评论全部”消失”（其实还在 GitHub 上，只是页面上匹配不到）。

Giscus 支持几种 mapping：pathname（路径）、url（完整 URL，换域名就死，最差）、title（页面标题）、og:title、specific（自己指定固定词条）。

和路径、域名都无关的是后三种。 对 Hexo 站点最实用的是 title——用文章标题做匹配，改域名、改 root、改 permalink 都不影响。代价是：以后改文章标题，评论会对不上。

💡 什么时候换最划算：现在这个决定跟"评论数量"直接相关。评论为 0 时换，成本是 0；有 50 条评论时换，就是 50 条评论失联。本站评论还很少，所以现在改一行配置，就是最便宜的时刻。
改法：主题 _config.yml 的 giscus 段把 mapping: pathname 改成 mapping: title，重新生成即可。

第四件：permalink 定死别再动。 :year/:month/:slug/ 这个结构一旦有文章被搜索引擎收录、被外部引用，改它就是全站 404。想加分类前缀、想去掉月份——在只有三篇文章的时候改，别在三十篇的时候改。

至于 CNAME 文件：现在不用建。它是给自定义域名用的，等买了再放——但你现在就该知道它放在哪（source/CNAME，内容只有一行域名，构建后会出现在 public/CNAME），免得到时候现查。

八、真到那天：迁移六步

假设半年后你买了域名，按这个顺序做：

第 1 步 · 买域名，先别急着解析。 在 GitHub 账号设置里做一次域名验证（加一条 TXT 记录），防止别人抢注你的子域挂内容。

第 2 步 · 加 DNS 记录。 根域名用四条 A 记录指向 GitHub Pages 的 IP；www 用 CNAME 指向 你的用户名.github.io。别用通配符 *.example.com，那会留下被接管的口子。

第 3 步 · 仓库设置里填自定义域名，勾上 Enforce HTTPS。 证书签发可能要等几十分钟到几小时。

第 4 步 · 改 _config.yml。 url 换成新域名，root 按实际情况改（放根目录就是 /）。

第 5 步 · 批量替换站内链接。 这一步取决于你走的是哪种写法：

bashbash
1
2
3
# 若 root 由 /Blog/ 变为 /，且链接是绝对地址
# 注意：先备份，再替换，别在生产目录上试
grep -rl 'molunanli.github.io/Blog' source/_posts/ | xargs sed -i 's|molunanli.github.io/Blog|yourdomain.com|g'

第 6 步 · 重新提交 sitemap，并在旧地址留一句”已迁移”。 搜索引擎需要主动通知，等它自己发现要好几天。

九、别被”换域名会掉权重”吓住

网上流传”换域名 SEO 归零”，这话不准确，但也别当耳旁风。客观地说：

  • 会掉，但通常是暂时的。搜索排名会波动几天到几周，然后按新地址重新稳定
  • 前提是旧地址能正确跳转。而 GitHub Pages 是静态托管，你自己没法配 301 规则（没有 .htaccess、没有服务端）。能做的只有：依赖 GitHub 对默认域名的重定向、重新提交 sitemap、把站内链接全部指向新地址
  • 对个人博客影响有限。你的流量大头通常是社交分享和搜索长尾，不是首页权重

所以真实的结论是：换域名对小站的影响被高估了，但”旧链接全断”这件事被低估了。 前者是玄学，后者是实打实的 404。

📌 一个诚实的边界这一节里关于"GitHub 重定向行为"和"SEO 波动幅度"的描述，一部分来自官方文档，一部分来自社区经验，我没有做过 A/B 实测。真正要买之前，建议按第四节说的用临时子域跑一遍——那个结果比任何文章都可靠。

十、把”留后路”当成一种习惯

写完这一篇，我回头把 about 页那 7 个 404 修了。修的时候有个感受：

这类问题从来不是”技术难”，是”没人检查”。 一条 sed、一个 grep、一次线上 curl，任何一步都能提前发现它。但我当时写完看了一眼页面觉得”挺正常”，就发布了。

所以”留后路”的真正含义，不是提前研究域名怎么买，而是：

  • 全站只有一种链接写法，将来一条命令改完
  • 图片和链接的处理方式心里有数，不靠猜
  • 评论绑定用与地址无关的键，锁死内容
  • 每发一篇，跑一次链接检查，而不是”看着没问题”

这四件事都不花钱，但能让你在真正需要换地址的那天，只花半小时。
