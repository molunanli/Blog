把你的 Hexo 主题发布出去：GitHub + npm + 官方主题列表，小白完整指南

✍️ 博主 📅 令和8年9月7日 ⏱ 阅读约 15 分钟
#Hexo #GitHub #教程 #mangaka #npm

做出一套主题只自己用，多少有点可惜。让全世界的人 npm install 一条命令用上你的主题、给你提 issue、甚至帮你改进——这既是分享，也是这套主题最好的”质量测试”。

这篇文章以本站正在使用的 mangaka 主题（日式漫画风那套）为例子，把发布主题的整条流水线走一遍。你不需要有自己的主题也能看懂流程；有的话，把文中的 mangaka 换成你的主题名就行。

一、发布前的自查清单

先别急着打包，用三分钟确认你的主题”能见人”。

1.1 认识主题的标准结构

Hexo 官方文档定义的主题由这几部分组成，发布前逐一对一下：

文件/文件夹 作用 发布时
_config.yml 主题配置文件（注意与站点根目录的 _config.yml 区分） 必须
layout/ 模板文件（ejs / njk / pug），决定页面怎么呈现 必须
source/ CSS / JS / 图片等静态资源 必须
languages/ 多语言文案（i18n），没有则界面语言写死在模板里 强烈建议
scripts/ 启动时自动加载的 JS（自定义辅助函数等） 可选
package.json npm 包信息，npm 发布必须有 发布 npm 必须
README.md 使用说明 + 截图，别人对你的第一印象 强烈建议
LICENSE 开源许可协议 强烈建议

1.2 先在本地”验货”

发布出去的每一处报错，都会变成用户在 issue 里对你的第一印象。发布前至少做三件事：

  1. 干净环境完整跑一遍：hexo init 建一个临时博客，把主题配进去，新建文章、页面、分类、标签各测一轮，确认不报错、排版不破（尤其手机宽度）。你平时用的博客已经”养熟”了，干净环境才能暴露依赖遗漏。
  2. 跑官方单元测试台：官方提供了一个专门测主题的仓库 hexo-theme-unit-test，里面预置了几乎全部页面类型和边界场景。操作：
shellshell

git clone https://github.com/hexojs/hexo-theme-unit-test.git
cd hexo-theme-unit-test
npm install
# 把你的主题放进 themes/ 目录（或按第四节方法用 npm 安装），
# 然后把 _config.yml 的 theme 改成你的主题名
hexo server

打开预览逐页检查：只要有不渲染、报错、明显错位的页面，就是发布前必须修的问题。
3. 配置全部给默认值：主题 _config.yml 里每个可选项都写好默认值，用户不配置也能正常跑——很多”装上就白屏”的差评，根源都是主题作者漏了默认值。

发布的是主题源码，不是你的博客现场。打包前清掉这些：

二、命名与”三件套”：让主题有户口

2.1 命名规范

Hexo 生态约定主题统一以 hexo-theme- 开头，命名全小写：

场景 命名 例子
主题文件夹 xxx themes/mangaka/
npm 包名 hexo-theme-xxx hexo-theme-mangaka
GitHub 仓库名 hexo-theme-xxx hexo-theme-mangaka
用户配置 theme: xxx theme: mangaka

npm 包名有硬性规则：只能小写字母、数字和 - _ .，不能以 _ 或 . 开头。大写字母会被 npm 拒绝。

为什么用户配置 theme: mangaka 而包名是 hexo-theme-mangaka？因为 Hexo 解析 theme: 配置时会按顺序在两个地方找：站点 themes/ 目录下的同名文件夹，以及 node_modules/ 里 hexo-theme- 前缀的包。所以你的包名必须带前缀，用户却不用管前缀——这也是第四节 npm 安装能直接生效的原理。

各字段的讲究：

字段 说明
name 必须与 GitHub 仓库名一致，且以 hexo-theme- 开头
version 语义化版本号，见 4.6 节
keywords **务必包含 hexo-theme**——npm 搜索和 Hexo 生态靠它发现你
license 与 LICENSE 文件保持一致
repository 指向你的 GitHub 仓库，npm 页面会自动显示”Repository”入口
files 打包白名单：只把这些目录/文件发上 npm。防止把杂七杂八的东西打进去，也决定包体积（越小用户装得越快）
engines 声明支持的 Node 版本，可选

官方 Landscape 主题的 package.json 只有 name / version / description / repository / keywords / license 六行——字段可以精简，但 name、version、license 别省。

## 许可

2.4 选一个 LICENSE

⚠️ 不写 LICENSE = 默认"保留所有权利"没有 LICENSE 文件的作品，在法律上默认不允许别人复制、修改、分发——你的主题等于"只能看不能用"，反而没人敢碰。发布开源主题，至少加一个 MIT 协议：允许任何人自由使用、修改、商用，只需保留版权声明。做法：在 GitHub 建仓库时下拉选 MIT（见 3.1），它会自动生成 LICENSE 文件。

三、第一步：把主题放到 GitHub

npm 包建议有公开的源码仓库（repository 字段、issue 反馈、版本 tag 都靠它），官方主题列表也要求提供仓库链接。顺序上先做这步。

3.1 建仓库

  1. 打开 https://github.com/new
  2. Repository name 填 **hexo-theme-mangaka**（与 package.json 的 name 一致）
  3. 选 Public（Private 的话别人装不了、也收不进官方列表）
  4. Description 写一句话介绍；License 下拉选 MIT（顺手把 LICENSE 文件生成了）
  5. 点 Create repository

四、第二步：发布到 npm（主力分发）

npm 是今天 Hexo 主题最主要的安装渠道。发布后，用户在你的 README 里复制一条命令就能用。

4.1 注册并登录 npm

  1. 到 https://www.npmjs.com 注册账号（用户名就是你的发布身份）
  2. 回到终端，在主题目录里登录：
shellshell
1

预期看到：按提示输入 Username、Password（npm 现在要求用邮箱验证码或一次性密码 OTP，跟着提示走）。登录成功后再确认一次身份：

shellshell
1
2
npm whoami
# 输出你的 npm 用户名即成功

4.2 国内用户先切到官方源（关键一步）

如果你配置过淘宝等 npm 镜像（npm config get registry 输出不是 npmjs 官方地址），发布会失败或报无权——镜像源通常只读。发布前切到官方源：

shellshell
1
2
3
npm config get registry
# 如果输出 https://registry.npmmirror.com 之类的镜像地址，执行下面两行：
npm config set registry https://registry.npmjs.org/
⚠️ 发布完记得切回镜像切到官方源后，下载依赖会变慢。发布完成后可以切回镜像（国内下载更快）：`npm config set registry https://registry.npmmirror.com`。发布动作本身不受影响——publish 永远直连 npmjs。

4.6 发新版本：改动后的标准流程

主题永远不会一次写完，改 bug、加功能后要发新版。语义化版本（SemVer）三档规则：

你改了什么 命令 版本变化
修 bug / 样式小调整 npm version patch 1.0.0 → 1.0.1
加新功能（向后兼容） npm version minor 1.0.0 → 1.1.0
破坏性改动（改配置项、换结构） npm version major 1.0.0 → 2.0.0

流程：

shellshell
1
2
3
4
# 在主题目录，改完代码、提交到 git 之后：
npm version patch        # 自动把版本号 +0.0.1 并打 git tag v1.0.1
git push && git push --tags
npm publish              # 发布新版本
💡 你的主题还没做 git 仓库？`npm version` 依赖 git 打 tag。如果主题目录还没 `git init`（先跳过了第三节），可以用 `npm version patch --no-git-tag-version`——只改 package.json 里的版本号，不打 tag。之后补做第三节的 GitHub 流程时再手动 `git tag v1.0.1`。

4.7 npm 常见错误速查

报错特征 原因 解法
code E401 Unauthorized 未登录或登录过期 重新 npm login
code 403 You do not have permission to publish "hexo-theme-xxx" 包名已被别人占用 换名字（先 npm view 包名 查重），或联系占用者
code 403 You cannot publish over the previously published versions 版本号没变就重复发布 执行 npm version patch 后再 npm publish
装出来样式全丢 / 白屏 files 白名单漏了 source/ 或 layout/ 补进 files 后发新版
publish 一直超时或 403 用了淘宝等镜像源 按 4.2 切回官方源

五、第三步：提交官方主题列表（被 hexo.io 收录）

六、发布后的日常维护

上线只是开始，维护决定口碑：

  • 认真回 issue：用户报的每个 bug 都是免费的测试报告，优先修”装上就跑不起来”类问题
  • 改动即发版：小修复也发 patch，别攒着（用户 npm update 就能拿到修复）
  • README 保持新鲜：截图过时、演示站挂掉都会劝退用户
  • 大版本写明兼容性：在 README 标注支持的 Hexo 版本（engines 里也能声明 Node 版本）

七、避坑与经验总结

⚠️ 四个最容易毁掉第一印象的坑① 没有 LICENSE——主题等于"保留所有权利"，没人敢用；② 没跑单元测试台就发布，用户一装就报错；③ 主题 `_config.yml` 里残留私人统计 ID / token；④ 用镜像源直接 `npm publish`，报 403 后还以为是权限问题。
💡 四条实战心得① 取名前先查重：`npm view 包名` 无输出说明名字可用；GitHub 上也搜一下同名仓库。② README 首屏放截图 + 演示链接，收录率、安装率都靠它。③ 版本勤发小步（patch），比憋大版本对用户友好得多。④ 时刻记住你发布的是"主题"——只包含模板、样式、脚本和配置模板，不要夹带任何个人站点内容。
